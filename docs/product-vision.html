SpecFlow · 从一个想法到一个上线产品

SpecFlow 让任何人能够快速生成符合自己要求的网页，由 AI Agent 细致管理，把好的设计沉淀成可复用物料， 并自动产出一份语言无关的产品规范（Spec），让 Cursor 等 AI IDE 接入 base 后端， 把设计稿一路编译成可上线的产品。

AI 驱动网页生成 物料沉淀 多风格 / Token PRD + Spec 自动产出 Cursor / MCP 链路 Supabase-like base
01

用户原话（来源）

我的目的是想能快速生成一个符合我要求的页面，然后我可通过 AI Agent 来很细致地管理我生成的页面， 并且我想把好的设计做成物料进行沉淀，这些物料可以替换、可以插入生成后的网页，也可以按某个风格生成， 每个设计风格都要有自己的 token 语言。

用户设计好了设计稿了，可以产出跟当前产品的各种物料、HTML 设计稿、设计语言、HTML PRD、Spec 文档， spec 要能让用户无论用什么语言都可以很好地还原。

并且后续我会提供一个 base，类似 supabase 等，让他能使用 cursor 等 IDE 工具快速开发出来产品并上线。
本文档是对上述想法的系统化整理 + 对话补充。决策记录章节标注了由用户拍板的内容。 技术实现层面请查看 架构方案文档。
02

产品的 5 大支柱

P1
快速生成符合要求的网页
用户输入需求 / 选风格 / 挑模板，AI 在几分钟内生成一个完整可见可用的网页， 不是 wireframe，是接近最终视觉的成品。
P2
AI Agent 细致管理
生成后，用户可以让 AI Agent 反复精细调整：改文案、换布局、换风格、插入新组件、替换物料。 每次修改都是结构化操作，可撤销、可追溯。
P3
好设计沉淀为物料
用户做出满意的设计片段，一键保存为物料。物料可被自己 / 团队 / 公开复用。 可在新页面里插入、替换现有节点、或被 AI 推荐使用。
P4
设计风格 = 一套 Token 语言
每个设计风格定义一套自己的 token（颜色、字号、间距、圆角...）。 物料和页面只引用 token 名，切换风格 = 切换 token 包，整页视觉立刻变样。
P5
从设计稿到上线产品
设计稿不只是一份 HTML，它能产出物料 / 设计语言 / PRD / Spec。 Spec 接入 Cursor + base 后端，让用户走完"设计 → 代码 → 上线"全链路。
5 大支柱合起来
不是另一个"AI 画图工具"
而是AI 时代的产品定义协议
03

关键产物 · 用户最终能拿走什么

一个完整的 SpecFlow 项目，向下编译会同时产出 6 类资产。它们是不同维度的"产物"，互相引用、互相约束。

01
HTML 设计稿（可直接预览的网页）
独立的 HTML 文件，含完整样式与交互（Alpine.js）。可直接打开预览、可上传到任意静态托管。
输出形态：page.html + assets/
02
设计语言（Token 包）
项目使用的完整 token 系统，含 primitive / semantic / component 三层，支持 light / dark 模式。可单独导出复用到其他项目。
输出形态：design-tokens.json + tokens.css
03
物料库（用户在此项目沉淀的物料）
用户在项目过程中保存的所有物料，含 Atom / Molecule / Organism / Template 四级。每个物料带 schema + 引用的 token slots + 参数。
输出形态：materials/ · 可独立分享、可上架到团队物料库
04
HTML PRD · 产品需求文档
从 Spec 自动渲染的人类可读 PRD 页面，包含需求条目、用户故事、流程图、数据模型表、验收标准、API 契约。本身也是一个网页，可导出可分享。
输出形态：prd.html · 编辑 PRD = 编辑底层 Spec
05
Spec · 语言无关产品规范 ⭐
终极产物。结构化 JSON，描述产品要做什么（意图 + 数据契约 + 页面契约 + 状态机 + 业务规则），不规定怎么做。 用户用 React / Vue / Solid / Svelte / Go / Python 都能从同一份 Spec 还原出同一个产品。
输出形态：spec.json + 派生 openapi.json / prisma.schema
06
Cursor / MCP 链路（远期）
通过 @specflow/mcp server，Cursor / Claude Code 实时连接 SpecFlow 项目，读 Spec、查物料、生成框架代码 stub。 配合 base 后端（Supabase-like），一键搭出可上线的应用。
未来形态 · 不在 v1/v2 主线，远期目标
04

用户需要理解的 5 个核心概念

Concept 1
风格（Style Family）
一套完整的设计语言，定义这个产品所有视觉的"基因"。Minimal Pro、Playful、Brutalist 等是官方内置风格； 团队也可以创建自己的风格。每个风格底下还有 light / dark 等模式变体。
用户操作：创建项目时必选 → 画布顶栏可"试换风格" → 一键还原
Concept 2
Token（设计令牌）
风格的"原子单位"。每个具体的颜色 / 间距 / 字号都是一个 token。物料和页面只引用 token 名（如 color.brand.primary），不写死 hex 值。所以换风格 = 换 token 包，物料结构不变，视觉立刻变。
用户基本无需直接面对 Token，但高级用户可微调（override）。
Concept 3
物料（Material）
可复用的设计片段。分四级（Atom / Molecule / Organism / Template）和三级归属（公共 / 团队 / 私有）。 物料能插入到任意页面、替换现有节点、按当前风格自动适配。
用户操作 1：从抽屉拖物料到画布 → 自动用当前风格的 token 渲染
用户操作 2：满意的片段 → "保存为物料" → 选归属（公开 / 团队 / 私有）
用户操作 3："替换为..." → 选同类物料 → 一键替换
Concept 4
PRD（HTML 化产品需求文档）
从 Spec 自动渲染出来的产品需求文档，是一个真实的网页。包含需求块、用户故事、流程图、API 表、验收标准。 编辑 PRD ≈ 编辑底层 Spec 字段。可单独导出给团队成员阅读。
关键：PRD 不是单独写的文档，它是 Spec 的可视化形态。
Concept 5
Spec（语言无关产品规范） ⭐
SpecFlow 的终极产物，结构化 JSON。描述产品要做什么、不规定用什么技术。 无论用 React / Vue / Solid / Svelte / 其他任何语言，从 Spec 都能还原同一个产品。
来源 1（自动）：用户在画布编辑时，系统从 Schema 结构自动推导 Spec 字段
来源 2（人工）：用户在 SpecPanel 上标注业务意图（"此字段必填"、"此按钮触发 X 流程"）
消费方：Cursor / Claude Code / 其他 AI IDE / 团队工程师
05

关键用户旅程

Journey 1 从零开始 · 创建项目

Step 1
用户登录 → 点击"新建项目"
Step 2
在风格选择页 选一个 StyleFamily（必选）。可从官方内置 / 团队风格 / 我的风格选
Step 3
（可选）选一个起始模板，或者从空白开始
Step 4
进入画布编辑器。AI ChatBar 主动询问需求："想做一个什么样的页面？"
Step 5
用户用自然语言描述 → AI 在 30 秒内生成初版 → 可见可点

Journey 2 AI Agent 精细管理

用户选中页面元素
点击画布中的任意组件 → 元素被选中 → ChatBar 自动 focus，附带选中元素的标签
下达指令
用户输入："把这个 Hero 的 CTA 按钮改成绿色，文案改为'立即体验'" → 发送
AI 处理
AI 通过 tool_use 输出结构化 SchemaOperation → 系统校验 → apply → 整页重渲
用户确认 / 撤销
不满意 Cmd+Z 撤销；满意继续下一轮对话。每次 AI 操作是一个独立撤销点

Journey 3 沉淀好设计为物料

用户对某个片段满意
比如做出了一个特别好看的定价表 → 选中整个区块
"保存为物料"
点击右键菜单 → 弹窗：输入物料名 / 选分类（Organism）/ 选归属（私有 / 团队 / 公开）/ 标 tags
系统处理
提取 schema 片段 → 识别引用的 semantic token slots → 提取可参数化的字段（标题、价格、CTA）→ 自动生成预览图
物料入库
物料出现在左面板"我的物料"/"团队物料" → 之后任意项目可拖入使用

Journey 4 试换风格

用户做完页面，想看不同风格效果
点击顶栏 "试换风格" → 弹出风格选择面板
选择新风格
从内置风格（Playful / Brutalist...）中选一个 → 点击预览
即时重渲
画布在 1 秒内整页重渲（token 替换）→ 视觉完全不同，结构和内容不变
用户决策
"应用" 永久切换风格 / "还原" 回到原风格 / 继续预览其他风格

Journey 5 产出资产 · 多形态导出

完成设计
用户在 TopBar 点击 "导出"
选择导出形态
勾选要导出的产物：HTML 设计稿 / 设计语言 / 物料库 / PRD / Spec / 全部
生成包
系统打包为 zip：page.html, prd.html, spec.json, design-tokens.json, materials/...

Journey 6 Cursor 接入 · 上线产品（远期）

用户安装 SpecFlow MCP
在 Cursor 配置 @specflow/mcp server，连接自己的 SpecFlow 项目
Cursor 拿到 Spec
通过 MCP 资源接口读取 spec://project/{id}，获得完整 Spec
生成代码 + 接 Base
用户对 Cursor 说："基于这份 Spec 生成 Next.js 项目，连接到 SpecFlow base" → Cursor 用 MCP tool 拿到数据模型 → 生成 Prisma schema、API、页面组件
一键部署
代码 push → base 服务自动 deploy → 用户拿到可访问的产品 URL
06

Agent 系统 · SpecFlow 是一张智能体网络

SpecFlow 不是"一个 AI 帮你画页面"，而是 9 个专业 Agent 协作完成产品定义。 用户只面对一个 ChatBar；底下有 Orchestrator Agent 拆解意图，分派给各专业 Agent 执行。 这是 Anthropic 推的 multi-agent pattern（Computer Use / Claude Code 同构）。

AI Chat ≠ AI Agent · 关键区别

维度 AI Chat AI Agent
输入一句话指令一个目标
流程单轮：问 → 答多轮：规划 → 执行 → 反思 → 调整
工具使用通常无必须有 + 自主选择
状态无目标记忆 + 进度
决策用户每步Agent 自主中间步骤

9 个 Agent 角色

每个 Agent 是"专家"，有自己的目标 / 工具集 / 触发时机。按使用模式分三类。

A · 用户主动调用（V2 MVP · 必做）
PageBuilder
页面构建
从需求生成完整页面
tools: search_materials, insert_material, switch_token, apply_schema_op
"做个 SaaS 着陆页，主打 AI 写作工具"
Editor
精细编辑
修改选中元素
tools: apply_schema_op, get_computed_style
"把这个 CTA 改得更显眼"
StyleCurator
风格策展
从灵感生成新风格
tools: image_analyze, extract_palette, create_style_family
"我喜欢 Linear 的风格，做一套类似的"
B · 主动建议型（V2 加分项）
MaterialCurator
物料策展
发现可沉淀的设计
tools: scan_pages, detect_pattern, suggest_save
触发：用户做完 3 个相似页面时
Reviewer
质量评审
检查页面质量问题
tools: check_a11y, check_consistency, check_responsive
触发：用户点"导出"前自动跑
Suggester
主动建议
给改进建议
tools: analyze_page, recommend_material
触发：用户停留某页 30s 无操作
C · 后台自动型（V3 远期）
SpecAuthor
Spec 作者
自动推导 Spec + 引导标注
tools: derive_spec, suggest_annotation
PRDWriter
PRD 编写
从 Spec 生成 PRD 内容
tools: render_prd_section, draft_user_story
CodeGenerator
代码生成 · Cursor 侧
把 Spec 编译为可上线代码
via MCP: search_materials, generate_data_model_code, render_page_to_framework

主控架构 · 用户视角 vs 系统视角

用户视角 · 单一 ChatBar
User: "把这个着陆页改成
       更专业的风格，
       加个定价区"

ChatBar:
  "好的，我已经：
   ① 切换到 Pro 风格
   ② 在 FAQ 上方插入定价区
   ③ 顺手检查了一致性
   有几处建议你看下..."
用户看到的是单一对话，体验流畅。
系统视角 · 多 Agent 协作
Orchestrator Agent
  │
  ├─ 拆解用户意图为子任务
  │
  ├→ StyleCurator
  │    "切到 Pro 风格"
  ├→ PageBuilder
  │    "插入定价区"
  └→ Reviewer
       "检查一致性"
  │
  └─ 汇总结果回复用户
底层是多个 Agent 串/并行协作。
为什么这种设计很重要
  • ① 专业化：每个 Agent 只懂自己领域，prompt 更短、cache 命中率高、错误率低
  • ② 可演进：增加新能力 = 加新 Agent，不动 Orchestrator 与现有 Agent
  • ③ 可观测：每次任务可见"哪个 Agent 做了什么"，便于调试和给用户反馈
  • ④ 可控成本：低频高价值任务（如 Reviewer）用强模型，高频任务用快模型
  • ⑤ 对齐用户原意：你最早说的"AI Agent 来很细致地管理我生成的页面"—— 多 Agent 才能"细致"
07

已对齐的关键决策

以下决策在对话中已与用户明确对齐。每条都附"原因 / 何时适用"以便后续 review。

# 主题 决策 原因
D1 真相源 Schema-as-truth · HTML = render(schema) AI 操作天然是结构化的；HTML 字符串作为真相源会持续产生反向同步等运行时复杂度
D2 交互运行时 Alpine.js（schema 表达意图，渲染器翻译） 15KB / 声明式 / 无 build / 覆盖 L1-L3 全部交互场景；不绑死，未来可加 React renderer
D3 物料归属 公共 + 团队 + 私有 三级 用户希望物料能自己用、团队用、也能被官方公开收录
D4 风格切换 先选风格，画布中可试换 · 严格 token 引用 AI 在明确风格语境内推荐质量更高；物料不内联 hex 才能一键换风格
D5 Spec 形态 结构化 JSON · 不是 HTML 用户希望"无论用什么语言都能还原"，JSON 是唯一语言无关的载体
D6 Spec 来源 双向：自动推导 + 人工标注 完全自动会缺业务语义；完全手写工作量大；冲突时人工优先
D7 Cursor 集成 JSON 导出（底层）· MCP server（主线）· SDK（可选） MCP 是 Anthropic 推的开放协议，已被 Cursor / Claude Code 等支持，是未来方向
D8 PRD 形态 PRD 也是 PageSchema · 复用渲染管线 不开发独立 PRD 工具；PRD 内容自动来自 Spec
D9 Base 范围 Supabase-like 后端 · 远期 · v3+ v1/v2 不做；Spec 设计要预留接口，让未来对接顺畅

还没完全拍板 · 待回答

以下问题已在对话中提出但尚未完全闭环。到对应实现阶段需要回头确认。

Q1 · 物料预览图怎么生成？
阶段 8 决定
候选方案：
  • • 方案 A：手工上传 — 简单但人工成本
  • • 方案 B：Puppeteer 服务端渲染截图 — 自动但要维护服务
  • • 方案 C：浏览器内 HTML2Canvas 截图 — 客户端但质量一般
用户当时回复："这个可以再讨论"，留待物料库阶段决定。
Q2 · 同一物料是否有"风格族变体"？
阶段 8 决定
当前方案：换风格时物料结构不变，仅 token 替换。 但有些场景（如 minimalist Hero ↔ playful Hero）结构差异较大，可能需要"同一物料 ID 在不同风格下挂不同 schema"。 v1 不做，等用户实际反馈再判断。
Q3 · 浏览器文件系统具体用在哪？
用户提出但未明确
用户问过"html 页面要在浏览器中开辟文件系统吗"，有三种可能解读：
  • • (a) 编辑器项目数据存浏览器本地（离线可用）
  • • (b) 生成的网站要有"上传文件 / 保存图片"功能
  • • (c) 在浏览器跑迷你 IDE 让用户改代码
技术选型差异大（IndexedDB / File API / OPFS+Service Worker+esbuild-wasm），需要用户在实际场景中再澄清。
Q4 · 团队物料的权限模型（RBAC）
阶段 8 决定
团队物料涉及"谁能看 / 谁能编辑 / 谁能发布"。决策需要等用户决定团队功能要做到多细（个人版起步 / 企业版需求）。
Q5 · base 后端的具体范围
v3+ · 远期
用户说"类似 Supabase"，但 Supabase 本身有：数据库 / 认证 / 存储 / Realtime / Edge Functions / Vector / 等。 SpecFlow 的 base 选哪些 MVP，等 v2 后期重新评估。
