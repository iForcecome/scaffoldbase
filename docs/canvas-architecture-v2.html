AI 用母语写设计：HTML + Tailwind 直接作为真相

v1 把 PageSchema（结构化 ComponentNode 树）作为真相，v2 直接把 完整 HTML 文档 作为真相。 Schema 层连同 SchemaOperation、component-registry、renderer 全部移除；AI 通过精确文本匹配 + data-sf-id 锚点定位修改任意 HTML，跟 Cursor / Claude Code 编辑代码同构。 样式用 Tailwind 工具类，AI 立刻能调用海量训练数据，做出真正像样的设计。

01

为什么从 schema-as-truth 转向 HTML-as-truth

触发点

v1 完工后让 AI "设计一个首页"，输出永远是 PageHeader + Section + DataTable 三件套—— 不是 AI 无能，是 schema 词汇表（~10 个语义组件 × ~3 个 variant）装不下设计师脑子里那张图。 Box 兜底也只是绕过 schema，并没有让 AI 用上母语。

v1 vs v2 全面对比

维度 v1 (schema-as-truth) v2 (HTML-as-truth)
真相源ComponentNode 树（结构化 JSON）完整 HTML 文档字符串
表达上限已注册组件 × variant 枚举HTML 的全部表达力
AI 训练熟悉度≈ 0（我们自造的词汇）极高（GitHub / docs 海量样本）
样式系统200 行手写 sf-* CSS + tokenTailwind v4 工具类 + 可选自定义 CSS
定位机制SchemaOperation 走 nodeIddata-sf-id 锚点 + 精确文本匹配（Cursor 风格）
上传 HTML 保真必须解析成 schema，信息有损原稿直接是真相，零损

  • • ESLint 禁止数据 store 互引
  • • Tool surface（P1 引入的）+ dispatcher + dry_run

  • • data-sf-id 选区机制

  • • page-schema/component-validation.ts

核心模型

三层真相 · Page / Project / Layout
interface Page {
  id: string
  title: string
  layoutId: string | null     // v2 始终 null（独立页）；v2.1 启用引用
  contentHtml: string         // 取代原 html 字段
                              // 独立页 = 完整 HTML 文档
                              // 走 layout = 只是"内容区"片段
                              // 所有可交互元素带 data-sf-id="sf-xxxxxxxx"
}

interface Project {
  id: string
  name: string
  sharedHead: string          // v2 启用：注入到每个页面的 <head>
                              // 适合：自定义 CSS / 字体 / 全局 JS / Tailwind config
}

// v2 阶段：数据模型一次到位，layouts 表已建但暂不读写
interface Layout {
  id: string                              // 'lay-xxx'
  scope: 'project' | 'team' | 'public'    // v2 强制 'project'；v3 解锁
  projectId: string | null                // scope='public' 时为 null
  parentLayoutId: string | null           // v2 强制 null；v3 启用嵌套
  name: string
  html: string                            // 完整 HTML 文档，含 {{content}} 占位符
  isDefault: boolean                      // 项目内默认
  createdAt, updatedAt
}

// schema 字段废除。DB pages.html 字段重命名为 content_html。
渲染合成（v2 阶段 = 简化路径；v2.1 启用 layout）
function renderPageForIframe(page, layouts, project) {
  let html = page.contentHtml
  if (page.layoutId) {                          // v2.1 启用
    const layout = layouts.find(l => l.id === page.layoutId)
    html = layout.html.replace('{{content}}', page.contentHtml)
  }
  return injectIntoHead(html, project.sharedHead)   // v2 启用
}
关键纪律：用户和 AI 永远不操作"合成后的 HTML"，只操作三个真相之一： page.contentHtml / project.sharedHead / layout.html。
三层真相
Page 内容 · Project 共享样式 · Layout 共享结构
零编译
没有 renderer，srcDoc = injectBridge(合成 HTML)
无解析层
tool 内部用浏览器 native DOMParser，零依赖
关键洞察 · "AI 母语"

AI 模型训练时见过的最多文本是 HTML + CSS + JS，其次是 各种 framework 代码。 ComponentNode JSON 这种我们自造的结构，AI 从来没见过、要现学，每个 prompt 都要重申词汇表。 切到 HTML 等于让 AI 用母语工作——质量、稳定性、token 效率全面提升。

为什么需要 sharedHead + Layout

没有共享层时，"统一所有页面主题色" / "改 Header" 这种诉求需要 AI 逐页 N 次 html_replace，对话啰嗦、易漏、token 贵。 sharedHead 解决 A 类（共享 CSS / JS / 字体），Layout 解决 B 类（共享 HTML 结构：header / footer / nav）。 v2 阶段数据模型一次到位（不返工）；sharedHead 立即启用；Layout 功能在 v2.1 启用。

工具集 · 10 个 HTML tool

Tool 是 product 的真正 API，UI 按钮和 AI agent 都通过 dispatchTools 派发。 HTML tool 全部走 html_set effect，由 dispatcher 调 editor-store.setPageHtml 落地，自动 push 历史快照。

读 · read

html_find按 tag/class/text/dataAttr 查找节点，返回 id + path 列表pageId, query: {tag, classContains, textContains, dataAttr}
html_get_computed_style通过 bridge 取渲染后的样式（读 paint 阶段值）pageId, nodeId

html_wrap用 wrapper 包裹 nodeId（升级容器层级）pageId, nodeId, wrapper
html_unwrap删除节点保留子节点（拍扁层级）pageId, nodeId

html_replace 精确匹配语义（Cursor 同构）

const occurrences = countOccurrences(page.html, old_html)
if (occurrences === 0) return { ok: false, error: { code: 'not_found', message: 'old_html 未匹配到' } }
if (occurrences > 1) return {
  ok: false,
  error: { code: 'ambiguous', message: '${occurrences} 处匹配，请在 old_html 加更多上下文', details: { count } }
}
const withIds = assignMissingIds(new_html)      // 给新片段缺失的 data-sf-id 自动补
const nextHtml = page.html.replace(old_html, withIds)
return { ok: true, effects: [{ kind: 'html_set', pageId, html: nextHtml }] }
AI 误判时唯一的反馈是 "ambiguous + count"，它会自动在 old_html 加更多上下文（前后兄弟节点 / data-sf-id）使其唯一—— 这是 Cursor / Claude Code 在生产环境跑了一年的鲁棒模式。

04

ID 策略

data-sf-id 规则
format:  sf-{8 char base36}        // 例: sf-7k9x2pqv
scope:   每个 page 内唯一       // 跨页不要求唯一
意义:    纯锚点，无语义           // AI 不需要"看懂"这串字符
赋予时机: ① 创建默认页时模板已带
         ② 上传 HTML 时 ingest walker 给所有元素补
         ③ tool 写入新 HTML 片段时 assignMissingIds 自动补
         ④ iframe 内 bridge-script 不再 assignIds（v1 那套删了）
为什么不让 AI 生成 id
  • • AI 重复造同样 id 风险高
  • • 增加 token 成本（写 id 不带语义价值）
  • • tool 内部 assignMissingIds 0 成本
AI 工作流
  1. html_read 看 HTML，里面所有 id 都暴露
  2. 认定要改的 id（或要插入位置的锚点 id）
  3. 调对应 tool；新片段不必带 id（自动补）
⛔ ID 纪律
  • • id 不承载语义，"sf-7k9x2pqv" 而不是 "page1.header"——v1 那种语义路径维护代价大
  • • 节点结构变了 id 也不变，便于持续编辑（修一处不影响别处）
  • • 不要用 id 做 CSS 选择器（用 class）
  • • 序列化时如发现非 sf- 前缀的 id，保留但不当锚点

Agent 协议（v2 微调）

服务端循环（agent.ts）
for (let turn = 1; turn <= MAX_TURNS; turn++) {
  choice = await callAI(messages, tools=[html_*, page_*, ...])
  if (choice.text) emit.text(choice.text)
  emit.step({turn, summary})
  if (no tool_calls) { emit.done(); return }

  for each tool_call:
    emit.toolRequest(callId, name, params)    // SSE 给 client
    pendingCallIds.push(callId)

  results = await Promise.allSettled(
    pendingCallIds.map(id => awaitToolResult(run, id))
  )
  messages.push(...results as role:'tool' content:JSON.stringify(result))
}

SSE 事件协议

事件 type 载荷 客户端动作
run_started{runId}存 runId 用于回报
text{text}累加显示
step{turn, summary}追加 trace
tool_request{callId, name, params}dispatchTools → POST /tool-results
done{}完成本次 turn
error{message}弹错

v2 System Prompt（核心摘要）

你是 SpecFlow 画布编辑器的 AI 设计 Agent。所有页面是完整 HTML 文档；样式用 Tailwind 工具类。

## 工作流
1. 调 html_read 看当前 HTML 结构和 data-sf-id
2. 决定改动后选 tool：
   - 改一段 HTML 区域 → html_replace（精确文本匹配；不唯一时多带上下文）
   - 插新区块 → html_insert（指定 anchorId + position）
   - 删节点 → html_remove
   - 改单个属性（class、href、src）→ html_set_attribute
   - 改纯文本 → html_replace_text
   - 升级层级（加包裹/拍扁）→ html_wrap / html_unwrap

## 设计审美
- 大量使用 Tailwind 工具类，不要写自定义 CSS
- 现代设计图案：hero / 渐变 banner / 卡片网格 / metric 大数字 / icon+文字
- 颜色：bg-gradient-to-br from-violet-500 to-fuchsia-500、text-slate-900、border-slate-200 等
- 圆角：rounded-2xl / rounded-3xl 比 rounded-md 更有现代感
- 间距：py-12 py-16 起步，small 时 py-6
- 字体：text-3xl/4xl/5xl 大胆使用；font-bold tracking-tight 是默认

## ID
- 不要自己造 data-sf-id，tool 内部自动补

## 终止
- tool 返回 ok:true 即成功，不要反复验证
- 改完给 1-2 句中文总结
08.5

多轮对话续接

当前实现的缺口（P2 留下的）

chat-store.sendMessage 每次都是全新 conversation——上一轮 messages 历史没传给下次 agent run。 结果：AI 一旦在某轮提问"用紫色还是蓝色？"，用户下条消息回"紫色"时，agent 看不见上下文，只看到孤立的"紫色"两个字——不知道紫色是什么。 这条不修，所有"问完用户再行动"的工作流都跑不通。

v2 改造

// chat-store 维护完整 conversation history
sendMessage(text) {
  const history = useChatStore.getState().messages   // 累积的 user+assistant 消息
  POST /api/projects/:id/agent {
    message: text,
    history: serialize(history),        // ← 新
    pageId, pageSchema, selectedNode
  }
}

// server agent.ts 用 history 拼 messages
runAgent(input) {
  const messages = [
    { role: 'system', content: buildSystemPrompt() },
    ...input.history,                   // ← 旧的 user/assistant/tool_calls/tool_results
    { role: 'user', content: input.userMessage }
  ]
  ...
}
History 该带什么
  • • user 消息：原样
  • • assistant 消息：text + tool_calls
  • • tool 消息：tool_call_id + content（结果 JSON）
  • • step 事件、SSE 元事件：丢弃
Token 控制
  • • 第一版直发全部 history，简单粗暴
  • • 真碰到爆 token 再做"老消息摘要折叠"
  • • Anthropic prompt cache 接 system + 早期 messages，缓解成本
  • • AI 自己可以 clear_conversation 显式重置（远期）

request_confirmation Tool · AI 显式提问

AI 不确定如何继续时，调这个 tool 把问题结构化发给前端。前端不只是显示文字——能渲染成选项按钮，用户点一下直接发送预填回复。 
request_confirmation {
  description: "需要用户确认时调用，等用户下次发消息再继续。",
  parameters: {
    question: string,           // 简洁、具体的问题
    options?: string[],         // 可选：枚举给用户挑的几个答案
    affectedPages?: string[]    // 可选：本次改动会影响的 page id 列表
  }
}
前端 ChatBar 渲染示意
AI 需要确认
把所有页面的主题色统一成什么？
影响 3 个页面：首页 / 订单管理 / 设置
点选项 = 自动发送该选项的文本作为下条用户消息 + tool_result {answered: '紫色'}。AI 续接同一 conversation 继续执行。
什么时候 AI 该提问
  • • 跨页一致性改动（颜色/字号/共享 Header 等）
  • • 用户描述模糊（"让首页更好看"——好看是什么风格？）
  • • 不可逆操作（删除多个页面 / 大段重写）
  • • 影响范围 ≥ 2 个页面 / ≥ 5 个节点时建议先告知再做
⚠ 反过来，单页小改动（改一句文案、调一个颜色）不要额外问——AI 直接做就好。过度请求确认会让交互变啰嗦。
08.6

跨页操作（多页面整体调整）

v2 每页是独立 HTML 文档，没有跨页耦合。跨页一致性靠 agent 多轮工作流而非数据层共享。 这条决定让 v2 模型简单（不引入 shared layer），代价是 AI 改"统一所有页的某个东西"时要 N 次 html_replace。 但因为 AI 是 agent loop + 多轮对话，这件事它能自己规划自己执行，用户体感跟"批量改"一样。

典型工作流

User: 把这几个页面的主题色统一一下

Turn 1  AI → page_list()                           // 看有多少页
        ← [{page-1,首页}, {page-2,订单}, {page-3,设置}]

Turn 2  AI → html_read(page-1)                     // 看各页现在的色
        ← <html>...大量 bg-blue-* text-blue-*...</html>
Turn 3  AI → html_read(page-2) ← ...bg-emerald-*...

关键设计取舍

问题 v2 选择 理由
跨页一致性agent 多轮 + N 次 html_replace不引入 shared 层，模型保持简单；agent 能力承担"批量"
共享 Header/Footerv2 不做；v3 配合 Material/Symbol 一起做需要 id 命名空间 + fragment 引用机制，独立 phase
AI 要不要先看所有页由 AI 自主选page_list 拿清单后 AI 决定哪些必须读、按需 html_read。不一刀切
影响范围大时要不要确认是，调 request_confirmation≥2 页或不可逆操作建议先问；prompt 中写死纪律
怎么 undo 跨页改动每个 html_set effect 独立快照用户按 N 次 undo 逐页回滚；v3 可加"批量 undo"
prompt token 成本直发 history；爆了再做摘要先观察，过早优化没意义

"AI 选要读什么"的 prompt 引导

## 多页操作纪律
- 用户说"这个页面" → 只看当前 pageId
- 用户说"所有页面" / "整体" / "统一" / "每个页面" →
   1. 先 page_list 拿清单
   2. 逐个 html_read（不要并行调一堆，loop 是串行的）
   3. 评估改动是否模糊，模糊则 request_confirmation
   4. 用户确认后再执行 html_* mutate
- 改动会影响 ≥2 个页面时，务必先告知用户范围再行动
- 优先用 html_replace 的精确匹配做跨页同一字符串的批量替换；
  每页一次调用，不要试图"一个 tool call 改所有页"——目前没这种 tool

v3 远期：project_* 批量 tool

v2 完成后如果跨页场景用得多、AI 重复调用太啰嗦，考虑加 3-4 个跨页 tool。每条 tool 内部循环所有页面，AI 一次调用搞定。 
project_replace_all_pages(old, new) → 对所有页执行 html_replace；返回每页结果
project_set_attribute_all(selector, name, value) → querySelectorAll 跨页匹配
project_extract_to_fragment(pageId, nodeId) → 抽出为可引用 fragment（v3 shared 层入口）
不立刻做的原因：在没有共享层的情况下，这些 tool 本质还是批量循环；先观察 AI 用多轮单页 tool 的实际表现，再决定加不加批量 tool。过早抽象会绑死设计。
⛔ 跨页纪律
  • • 影响 ≥2 页且模糊的请求 → 必须先 request_confirmation
  • • 不要把所有页 html_read 都塞 prompt——大项目会爆 token，按需读
  • • 跨页改动失败时（某页 html_replace 没匹配上）报告用户并停下，不要悄悄跳过
  • • 跨页改动完成后必须给汇总："共改了 N 页 / X 处"——让用户能验证

v2 共享层 · 让"逐页改"成为最后手段

上面那种"AI 多轮 + N 次 html_replace"是最差但永远可行的路径。当影响范围是"所有页面的同一个 header / 同一种主题色"时，应该走共享层：改 1 次，N 页自动跟随。

用户诉求 最优路径 阶段
统一所有页面主题色 / 字体project_set_shared_headv2
注入埋点 / Tailwind configproject_set_shared_headv2
统一所有页 header / footerlayout_updatev2.1
某页内文案 / 颜色调整html_replace / html_set_attributev2
删除/添加跨页共有节点layout_update（如有 layout）/ html_* 逐页v2.1 / v2
AI 决策顺序（写入 prompt）
  1. 能用 project_set_shared_head 解决？→ 用它（v2 已可用）
  2. 否则能用 layout_update 解决？→ 用它（v2.1 起）
  3. 否则 = 真实的跨页 N 次 html_* 操作 → 先 request_confirmation 再逐页改

关键差异：iframe 不再"修改"DOM

v3 远期：在 HTML 上叠语义

HTML 是真相，但产品形态需要 spec / material / token 等高层抽象。v3 不再造结构化 schema，而是在 HTML 节点上叠加 语义属性——AI 和工具读 DOM 的 data-* 属性提取语义层。

语义属性约定

<section data-sf-id="sf-7k9x2pqv"
         data-sf-component="PricingTable"      // 该节点是个"定价表"
         data-sf-role="cta-block"               // 在页面里担当 CTA 区
         class="bg-gradient-to-br from-violet-500 to-fuchsia-500 ...">
  <h2 data-sf-role="title">Pricing</h2>
  <button data-sf-role="action"
          data-sf-action="navigate:pricing">Get Started</button>
  <div data-sf-bind="plans[]">          // 数据绑定占位
    ...
  </div>
</section>
Spec 派生
walk DOM 找 data-sf-action / data-sf-bind / data-sf-component → 生成 spec.pages[].actions / data.models。架构等价于 v1 的 spec.derive，但走 HTML。
Material 库
Material = HTML 片段 + 占位符。{{title}} 模板替换实例化。比"参数化 ComponentNode"还简洁。
Token 系统
Tailwind config.theme.extend 从项目 token 派生；切风格 → 修 head 里 tailwind.config 注入 → 整页重渲。
为什么这条路更可持续

HTML + data-* 属性是 web 二十年的语义层标准（microdata / RDFa 同套思路）。 AI 训练数据里大量样本就是"div + 语义 class + data 属性"的组合， 我们叠 data-sf-* 等于给 AI 一套它已经会的标记语言——比让它学新 JSON schema 自然得多。

风险与权衡

R1 · AI 生成的 HTML 不闭合 / 嵌套错
对策：DOMParser 容错（即便有错也会出树），serializeDoc 自动补 closing tag。极端情况 tool 返回 invalid_html 让 AI 重试。可加一个轻量验证（用浏览器 native template parser）阻止无脑接受残破 HTML。
R2 · html_replace 不唯一时 AI 反复试
对策：error.message 明确写"${count} 处匹配，请加更多上下文（前后兄弟节点或 data-sf-id 锚点）"；prompt 教 AI 第一次不唯一就立刻扩 old_html 范围。Cursor 跑了一年验证这模式鲁棒。
R3 · Tailwind CDN 加载失败
对策：在画布编辑器自身的 dist/ 里 self-host 一份 Tailwind v4，作为备选。iframe 模板里加 <script onerror=""> 回落。v3 时整体切 precompiled-css 路线，按需打包。
R4 · 整页重灌 srcDoc 性能
每次 setPageHtml iframe 全量重渲——拖滑块改 padding 时每帧都重建很卡。 对策：① 拖拽期间走 bridge 直接 mutate iframe DOM（不进 store），松手才 commit；② 渐进策略：scoped 切换到 contentDocument.body.innerHTML 替换（保留 head）；③ 远期接 Service Worker 多文件方案（架构文档 §15.8）。
R5 · history 快照体积大
每个快照是完整 HTML 字符串，大页面可能 100KB+，几十步 undo 累计几 MB。 对策：① undoStack 限长 50；② 远期接 diff-match-patch 存 patch 而非全文。
R6 · v1 已有数据怎么办
对策：DB 已经清空，旧 schema 数据已不存在。即便存在，v1 时 page.html 字段一直在维护（renderPageSchemaToHtml 输出），β1 启动后老页面也能 load——只是没有 Tailwind 风格、需要 AI 重新设计。
R7 · 失去 schema 后 spec 派生怎么办
v2 不立刻做 spec 派生（v3 工作）。届时方案是走 DOM 找 data-sf-* 语义属性（见 §10）。 架构上等价 v1 的 spec.derive(schema) → spec.derive(html)，实现复杂度甚至更低（HTML walker 比 ComponentNode walker 更直观）。
