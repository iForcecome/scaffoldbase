Token 系统

L1 · Primitive
原子值
color.blue.500  = #3B82F6
space.4         = 16px
radius.md       = 6px
fontSize.lg     = 18px
shadow.1        = 0 1px 3px ...
具体值。风格作者一次定义。
L2 · Semantic
语义引用
color.brand.primary
  → color.blue.500

space.s          → space.4
text.body        → fontSize.base
surface.raised   → color.gray.0
物料/Schema 只引这层。 换风格只换 primitive 映射。
L3 · Component
组件级（自动推导）
button.primary.bg
  → color.brand.primary

button.primary.text
  → color.brand.contrast

card.shadow      → shadow.1
从 semantic 派生。一般无需手动维护。
StyleFamily + Mode 结构
interface StyleFamily {
  id: 'minimal-pro' | 'playful' | 'brutalist' | string
  name: string
  modes: {
    light: TokenSet  // { primitive, semantic, component }
    dark:  TokenSet
    [k: string]: TokenSet  // high-contrast 等可扩展
  }
  defaultMode: 'light' | 'dark'
}

// 一个 SpecFlow 项目持有：
project.theme = {
  family: 'minimal-pro',
  mode: 'light',
  overrides?: TokenSet  // 用户在风格上的自定义微调
}
切风格 = 大改造
换 StyleFamily（如 minimal-pro → brutalist）会让整页视觉完全变样。 前置确认对话框 + 一键还原。物料和 schema 不动。
切 Mode = 小改造
light ↔ dark 是同一 family 内的子集变体。可频繁切换，甚至跟随系统。 primitive 不同，semantic 名相同。
⛔ 强制纪律
  • • 物料 schema、PageSchema、组件渲染器 禁止内联 hex 值，必须引用 semantic token 名
  • • ESLint / 校验层强制 — 内联颜色 = 编译错误
  • • 例外：用户最终覆盖的 overrides 字段可以是具体值

Material 类型定义
interface Material {
  id: string
  name: string
  category: 'atom' | 'molecule' | 'organism' | 'template'
  tags: string[]                      // 'hero', 'pricing', 'form', ...
  preview: { thumb: string, large?: string }
  scope: 'public' | 'team' | 'private'     // 三级归属
  ownerId?: string

  schema: ComponentNode               // schema 片段（含意图节点）
  tokenSlots: string[]                // 引用的 semantic token 名

  parameters: MaterialParameter[]     // 可配置参数 (title, ctaText...)
  variants?: MaterialVariant[]        // 'compact' | 'feature' | ...

  styleFamilyHint?: string[]          // 适合哪些风格（软提示）
  version: string
  createdAt, updatedAt
}

interface MaterialInstance {          // 物料实例化后注入 schema
  materialId: string                  // 来源物料
  variant?: string
  params: Record<string, unknown>
  overrides?: Partial<ComponentNode>  // 用户对实例的局部覆盖
}
插入
用户从抽屉拖物料到画布 → instantiate(material, theme, params) → 生成 ComponentNode → MaterialOp(insert) → 加入 schema 树
替换
选中现有节点 → 右键 "替换为..." → 推荐同类型物料 → 用新实例替换该节点 → 保留可映射的 params
按风格生成
画布按当前 theme.family 过滤物料抽屉。AI 推荐时只考虑当前风格下评分高的物料。切风格自动重渲，无需重新插入。
归属与检索
scope 谁能看 谁能改 存储
public所有用户SpecFlow 官方仓库内置 + CDN
team团队成员团队管理员服务端 + RBAC
private仅自己用户本人服务端 + uid
检索时合并三个来源，按相关度排序。AI 推荐优先 team / private 中带"已使用"标记的物料。
08

Layout & Symbol · 跨页面复用

网站不同页面有大量共享部分（导航栏、菜单、Footer）。当前 Material 只解决"跨项目复用"，项目内多页面共享是空缺。 本章引入 Layout（整体骨架 + 命名 slot）与 Symbol（任意粒度的引用块）两个概念，与 Material 形成清晰分工。

8.1 三层复用机制对比

维度 Material Symbol Layout
范围跨项目项目内项目内
引用方式复制（独立副本）引用（链接）引用（骨架 + slot）
改源 → 实例❌ 不同步✅ 同步✅ 同步
粒度任意任意整体骨架
典型用途"好用的定价表"模板项目内导航 / CTA / Banner全局 Header/Sidebar/Footer
类比Figma 库组件Webflow SymbolNext.js Layout
一句话区分：Material 是"克隆"，Symbol 是"引用"，Layout 是"骨架 + 槽位"。

8.2 Layout 设计

interface Layout {
  id: string
  name: string                    // 'Main Layout' / 'Marketing' / 'Auth'
  schema: ComponentNode           // 含 <Slot name="..." /> 占位节点
  slots: SlotDefinition[]
}

interface SlotDefinition {
  name: string                    // 'main' / 'sidebar' / 'header-extra'
  required: boolean
  default?: ComponentNode         // 槽位空时显示的默认内容
  constraints?: {
    maxNodes?: number
    allowedComponents?: string[]
  }
}

interface Page {
  ...
  layoutId?: string               // 引用 Layout（可选）
  slots: Record<string, ComponentNode[]>     // 填充各 slot
  sections?: ComponentNode[]      // 无 Layout 时直接挂内容
}
示例 · 管理后台的 MainLayout
MainLayout schema:
└── div (root)
    ├── AppHeader (引用 Symbol "main-nav")
    ├── div (flex)
    │   ├── Sidebar (引用 Symbol "main-sidebar")
    │   └── Slot name="main"            ← 每个页面自己填
    └── Footer (引用 Symbol "footer")

Page "订单管理":
  layoutId: "main-layout"
  slots: { main: [OrderTable, OrderFilters, ...] }

8.3 Symbol 设计

interface Symbol {
  id: string
  name: string
  scope: 'project'                // 仅本项目
  schema: ComponentNode           // 任意 schema 片段
  parameters?: SymbolParameter[]  // 可被实例覆盖的字段
  usedBy: { pageId: string, count: number }[]   // 反向索引
  version: string
}

// schema 里出现的引用节点：
{
  component: 'SymbolRef',
  symbolId: 'main-nav',
  overrides?: {                   // 局部覆盖 prop（不影响其他实例）
    'activeItem': 'orders',
    'cta.label': '升级到 Pro'
  }
}
overrides 的价值
让同一个 Symbol 在不同页面有微小差异（如导航栏的"当前激活态"），不需要复制整个 Symbol。 改 Symbol 主体所有引用同步；overrides 是实例级，互不影响。

8.4 关键交互

① 提升为 Symbol
用户选中节点 → 右键 "提升为 Symbol" → 命名 + 选哪些 prop 暴露为 parameters → 原节点替换为 SymbolRef，Symbol 入库。
② 影响分析
编辑 Symbol 时顶部横幅："此 Symbol 被 7 个页面引用" + 列表（页面名 / 最近编辑时间）+ 选项 [应用到所有] / [分叉为副本]。
③ 分叉（detach）
某页想让 Symbol 实例独立演化：右键 SymbolRef → "解除关联" → 节点变成独立 ComponentNode 树，之后改 Symbol 不再影响此页。
④ Symbol 嵌套
✅ Symbol 可引用其他 Symbol（如导航栏内嵌搜索框）。⚠ 检测循环引用，编辑时报错。❌ Symbol 不能引用 Layout（避免逻辑混乱）。
⑤ 导出 Material 的处理
从含 SymbolRef 的节点导出为 Material 时，内部的 SymbolRef 自动 detach 成独立节点。跨项目无法保持引用关系。

8.5 Operation 扩展 · 6 类

原本 4 类 Op 扩展为 6 类。新增的 LayoutOperation 与 SymbolOperation 走同一 dispatch 入口。 
type LayoutOperation =
  | { type: 'createLayout',         layout }
  | { type: 'updateLayoutSchema',   layoutId, schema }
  | { type: 'addSlot',              layoutId, slot }
  | { type: 'setPageLayout',        pageId, layoutId }
  | { type: 'unsetPageLayout',      pageId }

type SymbolOperation =
  | { type: 'createSymbol',         from: { pageId, nodeId } }    // 提升
  | { type: 'updateSymbol',         symbolId, schema }            // 影响所有引用
  | { type: 'insertSymbolRef',      symbolId, targetId, position }
  | { type: 'detachSymbol',         refId }                       // 分叉
  | { type: 'overrideSymbolRef',    refId, overrides }            // 实例级覆盖
  | { type: 'removeSymbol',         symbolId }                    // 需先 detach 所有引用

8.7 撤销 / 保存 / dirty 的影响

  • • Symbol 改动是全局事件：所有引用页面都需要 mark dirty，UI 必须明确警示"将影响 N 个页面"
  • • 撤销 Symbol 编辑：影响所有引用页面 → history 快照需保存整个 project 的 schema + symbols + layouts
  • • 保存粒度：Layout / Symbol 单独存表；Page 只存 layoutId + slots + symbolRefs
  • • 删除 Symbol：必须先 detach 所有引用，否则报错（防止悬空引用）

8.8 Cursor / MCP 视角

MCP 新增能力：
  ├─ resource: layout://project/{id}/{layoutId}      // 读 Layout
  ├─ resource: symbol://project/{id}/{symbolId}      // 读 Symbol
  ├─ tool:     list_symbol_usages(symbolId)          // 影响分析
  └─ tool:     extract_layout_from_pages(pageIds)    // AI 自动提取共性 (v3)
Cursor 看到的是结构化的 Layout + Pages + Symbols，不是 N 份重复 HTML。生成框架代码时直接映射为 Next.js Layout / React Component。

8.9 V1 范围决断

问题 决断 理由
Layout 嵌套？❌ 不支持复杂度高，v1 单层 Layout 已覆盖 95% 场景
没有 Layout 的页面？✅ 允许Page.sections 作为默认，单页项目无需 Layout
AI 自动提取共性成 Layout？⏳ v3 远期PageBuilder Agent 的扩展能力
Symbol 嵌套 Symbol？✅ 支持合理需求，加循环检测
Symbol 跨项目（变 Material）？⚠ 只能导出为 Material导出时 detach 内部引用，跨项目无法保持链接
⛔ 设计纪律
  • • Symbol 删除前必须 detach 所有引用，禁止悬空 SymbolRef
  • • 编辑 Symbol 必须显示影响范围，禁止"无声修改" N 个页面
  • • Layout / Symbol 不能内联 token hex，与普通物料同纪律
  • • Symbol 引用 Symbol 必须检测循环，编辑器实时验证
  • • 导出 Material 时自动 detach 内部 SymbolRef，避免跨项目悬空
  • • history 快照需含 project-level 资产（layouts + symbols），撤销才能完整
09

交互运行时 · Alpine.js

选 Alpine 的理由
  • • 15KB，无 build，CDN 即用
  • • 声明式语法，schema 可对应
  • • AI 容易生成，用户拿走可读
  • • 完全覆盖 L1-L3 交互场景
明确边界
  • • L4 路由：自带 5 行 history API 实现
  • • L4 大列表：嵌虚拟滚动库
  • • L5 富文本：嵌 TipTap（按需）
  • • L5 图表：嵌 ECharts（按需）
⛔ 最重要的纪律
❌ 错误：schema 写 Alpine 字符串
{
  "component": "div",
  "props": {
    "x-data": "{ open: false }",
    "x-show": "open"
  }
}
→ AI 没法稳定生成、用户没法理解、换渲染器要全改

Spec · 语言无关产品规范

Spec 是结构化 JSON，不是 HTML。 它描述"产品要做什么"，不规定"用什么技术实现"。 Cursor 拿到 Spec 后，可以用任何框架（React / Vue / Solid / Svelte / Go / Python）还原同一个产品。 PageSchema 只是 Spec 的众多实现层之一（HTML 实现）。
Spec 结构
interface Spec {
  meta: { name, version, description }
  intent: string                  // 自然语言：这个产品要解决什么问题

  data: {
    models: DataModel[]           // 类 Prisma schema
    api: ApiContract[]            // 类 OpenAPI
  }

  pages: PageContract[]           // 每个页面要展示什么数据 + 用户能做什么
                                  // 不规定 UI 长什么样
  flows: UserFlow[]               // 状态机：用户从 A 页面到 B 页面的路径
  rules: BusinessRule[]           // 业务约束、计算公式、权限规则

  ui: {
    refs: PageSchemaRef[]         // 指向具体的 PageSchema 实现
    theme: { family, mode }       // 引用 Token 系统
  }
}

interface PageContract {
  id, path, title
  intent: string                  // 这个页面解决什么
  reads: DataQuery[]              // 需要哪些数据
  actions: Action[]               // 用户能做什么操作
  states: StateDescriptor[]       // loading/error/empty 等
  annotations: Annotation[]       // 业务标注：哪些字段必填、哪些计算
}
向上推导（自动）
用户在画布编辑时，系统自动从 PageSchema 结构推导出 Spec 字段：
  • • Form 节点 → PageContract.actions
  • • DataList 节点 → reads (数据查询)
  • • 多页跳转链接 → flows
  • • 节点 props → data.models 候选字段
向上标注（人工）
SpecPanel 让用户在 schema 节点上加业务标注，自动写入 Spec：
  • • "此字段必填" → rules
  • • "此按钮触发 X 流程" → flows
  • • "此列表对应 Order 模型" → data.models
  • • "此页仅管理员可见" → rules (权限)
导出格式
spec.json
完整 Spec，主要交付物
openapi.json
从 data.api 派生
prisma.schema
从 data.models 派生

部署模式 · 服务端 vs 前端

维度 服务端 Agent（推荐） 前端 Agent

Orchestrator Agent · 主控设计

  • ③ 选择合适的子 Agent，串联调用

Prompt 结构（cache-friendly）

Orchestrator 调用子 Agent 的 tool 定义示例

子 Agent 内部 · 仍然是 tool_use

子 Agent 收到 goal 后，自己也用 tool_use 调用具体工具完成任务。比如 PageBuilder： 
PageBuilder Agent 可用工具：
├── search_materials(query, category, scope)        // 查物料库

├── apply_material_operations(ops: MaterialOp[])    // 物料操作
├── apply_token_operations(ops: TokenOp[])          // 改风格
└── reply_to_orchestrator(summary, ops_applied)     // 完成回报

执行轨迹示例（用户："加个定价区"）：
  1. PageBuilder → search_materials("pricing", "organism", scope=all)

                     summary: "插入了 3 列定价物料，含 Free/Pro/Team",

渲染管线 · Schema → HTML 的编译过程

本章回答一个关键问题：Tailwind CDN、自定义 CSS、Alpine、JS 等 怎么和 schema 协调？ 答案是：它们都不进 schema。schema 只描述页面意图与结构，其余都是渲染产物或渲染器配置，由渲染管线自动生成。

14.1 边界 · 什么进 schema，什么不进

HTML 组成 进 schema？ 由谁产生
DOCTYPE / html / head 骨架❌渲染器固定模板
Tailwind CDN <script>❌渲染器配置（按需）
tailwind.config.colors 扩展❌从 TokenSet 派生
Google Fonts <link>❌从 token.fontFamily 派生
全局 reset <style>❌渲染器固定 (design-system/render-css.ts)
Alpine.js CDN <script>❌渲染器按需注入（有交互节点才注入）
内联 <script> 自定义 JS⛔ 禁止直接写走 Material runtimeDeps 或 AssetFile
<body> 内 HTML 结构✅ 唯一进的ComponentNode 树 → 渲染

14.2 五步编译流程

INPUT
  ├─ PageSchema      (页面结构 + 意图节点)
  ├─ TokenSet        (当前风格解析后的 token 值)
  └─ RendererConfig  (engine: 'tailwind' | 'css'; alpine: auto-detect; output: ...)

│
▼ Step 1 · 解析 token
    扫 schema 用到的 semantic token → resolve 出 primitive 值 → 形成 CSS vars

▼ Step 2 · 扫描意图节点 → 推断运行时需求
    见到 Disclosure / Tabs / Modal → 需要 Alpine
    见到 DataList                 → 需要 fetch helper
    见到任何用到的 Material        → 收集它声明的 runtimeDeps

▼ Step 3 · 生成 <head>（按需注入）
    DOCTYPE + viewport (固定)
    + Tailwind CDN + config (如果 engine=tailwind)
    + Google Fonts (从 token.fontFamily)
    + 全局 reset CSS (固定)
    + 设计 token CSS 变量 (从 Step 1)
    + Alpine CDN (如果 Step 2 有交互节点)
    + Material deps (如果 Step 2 收集到)

▼ Step 4 · 渲染 <body>
    递归 ComponentNode 树
    每个节点查 registry 找 renderFn
    意图节点 → 翻译为 Alpine HTML + 指令
    样式属性引用 token → 转为 utility class 或 CSS var

▼ Step 5 · 输出
    形成 ResourceBundle (详见 15 章)
    Editor: 序列化为单文件 srcDoc
    Export: 序列化为多文件目录

14.3 三层正交模型

Renderer Config · 渲染策略
engine / bundleStrategy / cdn vs self-host / output 模式
⊥ 任一层变化不影响另两层
Token Set · 设计语言
family + mode + overrides → resolve 后给渲染器
⊥
PageSchema · 页面结构
ComponentNode 树 · 唯一真相
切 token
视觉变，结构不变
切渲染器
HTML 实现变（Tailwind ↔ vanilla CSS），结构和视觉一致
切 schema
页面变，token 和渲染器不变

14.4 RendererConfig 字段

interface RendererConfig {
  output: 'single-file' | 'multi-file'
  bundleStrategy: 'inline' | 'extract' | 'cdn'
  tailwindMode: 'cdn' | 'self-host' | 'precompiled-css'
  alpineMode: 'cdn' | 'self-host' | 'auto'   // auto = 检测到意图节点才注入
  fontStrategy: 'google-fonts' | 'self-host' | 'system'
  minify: boolean
}

// 项目级配置，不在 PageSchema 里。同一项目所有页面用一致策略。

14.5 mock-pages 的映射示例

当前 mock-pages.ts 的 order-list 页面拆解：
<!DOCTYPE html><html><head>              ← 渲染器固定模板
  <script src=".../tailwindcss"></script>   ← RendererConfig (engine=tailwind)
  <script> tailwind.config = {              ← 从 TokenSet 派生
    theme: { extend: { colors: {...} } }
  } </script>
  <link href=".../fonts.googleapis...">     ← 从 token.fontFamily 派生
  <style>* { margin:0; ... }</style>         ← 渲染器固定 reset
</head>
<body>
  <header>...OrderHub...</header>            ┐
  <main><h1>订单管理</h1>...</main>          │ ← 仅这部分进 schema
</body></html>                              ┘
该页面的 schema 只需要描述 { sections: [AppHeader, PageTitle, OrderTable, ...] }，整个 head 不在 schema 里。
⛔ 设计纪律
  • • head 是按需组装的，空 schema 不注入 Alpine；只用 Hero 的 schema 不引 Chart.js
  • • token 不写死在物料里，物料只引 semantic 名（强制 ESLint）
  • • 切换渲染器（如未来加 React renderer）不需要改 schema
  • • RendererConfig 是项目级，不进 PageSchema

Assets 与文件系统 · 编辑期 vs 导出期

编辑期没有多文件概念。所有 CSS / Alpine 指令 / Material initScript 全部内联在一个 HTML 字符串，灌进 iframe.srcDoc。 导出期才有多文件。两种模式由 RendererConfig.output 切换，共享同一份核心渲染逻辑。

15.1 三种场景三种模式

场景 输出形态 原因
编辑器内 iframe 预览单文件 srcDoc速度优先 · 免文件依赖
用户导出 ZIP多文件项目目录可维护 · 可上传任意静态托管
Cursor / Base 接入多文件 + manifest.json工程化 · 可被 IDE 编辑

15.2 核心抽象 · ResourceBundle

避免"编辑期 / 导出期"维护双套渲染逻辑。渲染器内部统一产出 ResourceBundle（抽象的文件清单），最后一步序列化分叉： 
schema + tokens + materials
        ↓
   ResourceBundle           ← 渲染器核心产物
   {
     files: [
       { path: 'index.html',                content: '...' },
       { path: 'assets/tokens.css',         content: '...' },
       { path: 'assets/alpine.js',          kind: 'cdn', url: '...' },
       { path: 'assets/materials/chart.js', content: '...' },
       { path: 'data/products.json',        content: '...' },
     ]
   }
        ↓
   分叉序列化
   ├─ Editor:   bundle → 内联拼成一个 HTML 字符串 → srcDoc
   └─ Export:   bundle → 写成多文件目录 → zip
一份核心逻辑，两种输出。编辑期 / 导出期的差异只是最后一步序列化方式。

15.3 AssetFile · 一等公民

项目里的"代码 / 数据文件"作为独立实体存在，不藏在 schema 节点里。schema 通过 asset: 协议引用。 
interface AssetFile {
  id: string
  path: string              // 'scripts/analytics.js' / 'data/products.json'
  kind: 'js' | 'css' | 'json' | 'image' | 'font' | 'svg'
  scope: 'project' | 'page' | 'material'
  source: 'user' | 'material' | 'generated'
  content: string | Blob
  meta: {
    description?: string
    audited?: boolean       // 安全审核（私有/团队/公开物料的把控点）
  }
}

interface Project {
  ...
  assets: AssetFile[]
}

// schema 通过协议引用：
{ "component": "Chart",
  "props": { "dataSource": "asset:data/sales-2024.json",
             "config":     "asset:scripts/chart-config.js" } }

// 渲染时解析：
// 单文件模式 → 内联资源内容
// 多文件模式 → 转为相对路径 './data/sales-2024.json'

15.4 抽离规则 · 什么内联，什么独立

内容 编辑期 导出期 原因
全局 reset CSS内联assets/reset.css固定不变、独立缓存
Token CSS 变量内联assets/tokens.css换风格只换这一文件
Material 共享样式内联assets/materials.css多页面复用
Material initScript内联assets/materials/{id}.js调试、可复用

15.7 编辑期单文件 srcDoc · 为什么 + 局限

为什么选单文件
  • • srcDoc 本质是字符串，无文件系统
  • • 渲染器输出一个字符串就完事，简单
  • • iframe 重建不需等多文件加载，快
  • • 零额外依赖（无 SW、无 Blob URL）
局限（项目大了显现）
  • • 每次 schema 改一点 → 整个 HTML 重写 → iframe 全量重渲
  • • 浏览器无法缓存内联代码
  • • DevTools 调试不便（无文件名 / sourcemap）
  • • Material initScript 多了内联污染

15.8 升级路径 · Service Worker 多文件编辑期（v3）

如果未来出现以下信号，升级到 SW 方案：
  • • 单个项目 > 50 个组件，srcDoc 字符串 > 500KB，切页明显卡
  • • 用户反馈 DevTools 调试不便
  • • Material initScript 数量爆炸，互相污染
  • • 想加"分页懒加载"
编辑器启动时注册 Service Worker
       ↓
iframe.src = blob:editor/index.html
       ↓
iframe 内请求 ./assets/tokens.css
       ↓
SW 拦截 → 从内存中的 ResourceBundle 返回
       ↓
浏览器正常缓存、DevTools 正常显示文件名 / sourcemap
复杂度上一截，但单一渲染逻辑——不再分 srcDoc / 文件两套。
v1 / v2 不做，但架构里预留 ResourceBundle 抽象，未来只换最后一步序列化，核心不动。

15.9 与 base 后端联动（远期）

导出 / 部署时
  ├─ AssetFile 上传到 base 存储 (S3-like) → 拿到 CDN URL
  ├─ Material initScript 同理
  ├─ spec.data.api 派生 → base 自动生成 API endpoint
  └─ HTML 引用 base 提供的 URL

Cursor 通过 MCP 接入 (新增 MCP tool)
  ├─ read_asset(path)        // 读项目文件
  ├─ write_asset(path, content)  // 反向写回
  └─ list_assets()           // 列出所有 AssetFile
⛔ 设计纪律
  • • schema 仍是唯一真相。AssetFile 是 schema 的"被引用方"，不是平行真相
  • • 渲染器内部统一产出 ResourceBundle，单/多文件只是序列化差异，不要写两套渲染逻辑
  • • Alpine 指令永远内联在 HTML，不要尝试抽离到 JS 文件
  • • AssetFile 是一等公民，单独存储 + 单独可编辑 + 单独审核
  • • 切换输出模式不需要改 schema，是 RendererConfig 的事

风险与权衡

R1 · buildPageSchemaFromDomTree 不能 100% 还原
mock 页面是手写 Tailwind，可能丢信息。对策：保留 legacy html 兜底 1-2 周；个别页面允许"仅渲染、不可编辑"模式逐步重建。
R2 · 每次 op 重渲整页 — 性能
右面板拖滑块改 fontSize 每帧 op 可能卡。对策：① 拖拽中走临时 inline style preview，松手才 commit；② iframe 渲染策略改为 contentDocument 局部替换 body（不重写 srcDoc）。
R3 · AI 输出 4 类 Op 稳定性
让 AI 输出复杂 MaterialOp / TokenOp 比改文案难。对策：Anthropic tool_use + JSON schema 强约束；prompt cache 静态部分；分级支持（先支持高频 op，复杂场景 fallback 到 prompt 工程）。
R4 · "ESLint 禁止内联 token"会拖慢初期开发
物料作者会抱怨。对策：提供 codemod 工具自动把 hex → semantic 名；给 design-system 内部一个豁免清单（如 token 定义文件本身）。
R5 · Alpine 表达力上限
复杂应用（看板、协作）Alpine 不够。对策：schema 表达意图，未来加 React renderer 是免费升级路径。短期 v2 范围内不做 L5 场景。
R6 · Spec 推导 vs 标注的边界不清
用户标注与系统推导可能冲突。对策：规则——人工标注优先，自动推导只填空白字段；冲突时 SpecPanel 显示"推导 vs 标注"对比 UI 让用户拍板。
R7 · 阶段 7-11 跨度大，可能脱节
v2 范围工作量 ~30+ 天，需要持续投入。对策：每阶段独立产出可演示功能，不依赖未完成的下游；优先级 7→8→9→10→11。
