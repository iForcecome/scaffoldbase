产品概述

填补 AI 产品工具链中"从想法到可评审方案"的关键空白

核心问题

PM、创业者、产品负责人这个庞大群体被当前 AI 工具严重忽视。他们脑子里有产品想法，但没有快速把想法变成"可评审原型 + 可交付 PRD"的工具。

传统流程碎片化

写文档(Word/Notion) → 画原型(Axure/墨刀) → 给开发讲解 → 反复对齐，整个链路割裂且低效

AI 工具门槛高

v0/Cursor 要求懂代码，Figma 要求懂设计，ChatGPT 写 PRD 又拿不到原型

文档与原型脱节

PRD 和原型分开维护，随着迭代不断脱节，最终变成没人看的废纸

Design System & Asset Library

设计系统与物料库

解决 AI 生成"千篇一律"的根本问题——让 AI 在高品质约束下生成，而非自由发挥

核心痛点：AI 生成的东西缺乏"设计品味"

当前所有 AI 工具生成的页面都有严重的"AI 味"——千篇一律的渐变紫色、无意义的卡片堆砌、没有体系的间距和字号。根本原因是 AI 没有完整的设计规范作为约束。

Token 不完整

颜色随机挑、字号随意选、间距不统一，生成 10 个页面 10 种风格

交互无规范

按钮 Hover 没有动效、菜单没有展开动画、表格没有排序交互

无法"高大上"

用户想要专业感的网站，AI 只能给出粗糙的模板感

解决方案：三层物料体系

从 Token 到组件到页面，层层约束、层层精美

通过 MCP 协议与 Cursor/Claude Code 双向同步，让 Spec 在整个开发周期持续保鲜

没有 MCP
1. 用户导出文件
2. 离开 SpecFlow
3. 文件逐渐失效
✕ 三个月后 Spec 变废纸
有 MCP
1. 用户在 Cursor 开发
2. 通过 MCP 双向同步

读取类工具

get_spec(module) 读取模块 spec
get_design_tokens() 获取设计 token
get_component_spec() 组件 API
list_pending_features() 待实现功能

写入类工具

让 Cursor 更新 Spec

update_spec() 更新 spec
add_data_field() 添加数据字段

report_deviation() 偏离记录

校验类工具

最有价值的能力

validate_against_spec() 代码符合 Spec？
check_design_token() Token 使用正确？
find_undocumented() 未记录的变更？

完整工作流示例

开发者在 Cursor 里说：

"实现一下订单导出功能"

1 get_prd("订单管理") → 读取业务意图
2 get_spec("订单") → 读取数据模型
3 get_design_tokens() → 读取设计规范
4 get_component_spec("Button","Modal") → 复用组件
Cursor 生成代码

自动符合 PRD 业务逻辑、用对的字段、统一的组件、遵循设计规范

5 update_spec("订单", {新增导出功能})
6 mark_feature_done("order_export")

MVP

MVP 阶段

1-2 个月 当前阶段

验证"对话 → HTML → Spec"最小闭环

做什么
  • ✓三栏布局：对话 + 预览 + Spec
  • ✓对话直出单文件 HTML
  • ✓Spec 三要素：页面、数据、Tokens
  • ✓支持下载 HTML + Spec 文件夹
不做什么
  • ✕物料库、模板系统
  • ✕画布精细调整
  • ✕Project Base / BaaS
  • ✕MCP、协作、版本历史

验证标准：找 5-10 个真实用户产出真实项目，看是否主动来用第二次、是否把 Spec 给开发看。

Competitive Moat

护城河分析

多重壁垒叠加，与 Cursor/Claude Code 共生而非竞争

🔒

工作流锁定

Cursor 每次写代码都通过 MCP 调用 Spec，停用会让开发流程变慢

📚

历史沉淀

项目用得越久，Spec 中的决策、迭代历史、业务上下文越多，迁移成本极高

🎯

领域 Skill 库

业务模板和 Skill 包是"产品设计经验"的封装，纯技术无法复制

🎨

Design Rules

"设计语汇→具体修改"的映射库需长期打磨，是经验型壁垒

📄

Spec 格式标准

如果被生态采纳成事实标准，会形成生态依赖

👥

团队协作

多开发者通过 MCP 共享 Spec，团队对齐成本大幅下降

与 Cursor/Claude Code 的关系

共生而非竞争。SpecFlow 产出 PRD/Spec，Cursor 消费 PRD/Spec 写代码——上下游关系。不需要打赢 Cursor，只需要让 Cursor 用户离不开 SpecFlow。

Risk Analysis

风险与应对

表现：生成的 HTML 充满"AI 味"——千篇一律的渐变紫色、堆砌卡片，用户失去信任

应对：MVP 阶段最大投入在 Prompt 工程与设计审美训练；建立内部"生成质量评分"机制

表现：用户觉得 Spec 没用，只把 HTML 截图发给开发

应对：MVP 阶段每周访谈用户，迭代 Spec 结构；不要一开始把 Spec 设计得太重

表现：Pencil.dev、Cursor 等向上扩展加入 PRD 生成功能

应对：护城河必须建立在领域 know-how 而非纯技术；深度服务 PM 工作流

表现：目标用户走公司预算流程，决策周期长

应对：并行服务付费意愿更强的独立创业者；考虑 Team 版的销售策略

表现：支持单一栈市场窄，支持所有栈精度低

应对：先死磕 Next.js + Tailwind 这一套主流栈，做到极致再扩展

三条最重要的建议

在设计和实现过程中始终牢记

1

质量是 1，其他是 0

MVP 阶段所有花哨功能的前提是——第一次生成出来的东西就要好看、好用

2

找到灵魂场景

功能多不等于产品好。围绕一个最锐利的痛点构建，其他都是辅助

3

MCP 不要 MVP 做

MCP 是终极杀招，但要等 Spec 格式稳定了再打
